A workspace session is a session that does not belong to a task. It has no workflow steps. It uses the same session page as a [task session](/coding-sessions/#session-page). The agent can read your repository and create tasks.

<ProductDemo id="chat" />

## Start a workspace session [#start-a-session]

<ProductDemo id="new-session" />

<Steps>
<Step>Select the arrow beside <Action>New task</Action>, then <Action>New session</Action>. A draft page opens, and the sidebar shows it with the **Draft** badge.</Step>
<Step>Under the composer, choose the work location, the target branch, and a custom role if you need one.</Step>
<Step>Check the model in the composer. It starts with the [**Default model**](/models/#model-choice) of the repository.</Step>
<Step>Type your first message and send it. The startup steps show in the transcript, then the agent starts.</Step>
</Steps>

To start the session in another workspace, select the workspace name in the heading. You can leave the page while the session starts. A notification shows the steps until the session is ready.

In a collapsed sidebar, select <Action>+</Action>, then <Action>New session</Action>. You can also press the **New session** [shortcut](/keyboard-shortcuts/#default-keys), or run <Action>New session</Action> from the [command palette](/command-palette/).

| Work location | Where the agent works |
|---|---|
| **Current checkout** | In your repository folder, on its current branch. The agent changes the files of your checkout. |
| **New worktree** | In a new folder, on a new branch or an existing branch. Your checkout does not change. |
| **Existing worktree** | In a worktree that you select. Use it to continue work in the worktree of a task or an earlier workspace session. |

For **New worktree**, select the branch button next to the work location:

- **New branch**: the button shows <Action>Auto branch</Action> until you type a **Branch name**. With an empty **Branch name**, your first message names the branch. To name the folder, open <Action>Custom folder name</Action>. Otherwise, OpenDucktor gives the folder a unique name.
- **Existing branch**: the button shows <Action>Select branch…</Action> until you choose the **Local branch**. Then an empty **Folder name** takes the branch name, with a hyphen in place of each slash or other special character. The name cannot be empty.

The session compares its changes with the target branch. A new draft starts with the work location that you chose last.

A workspace session has no Goal mode. After the first message, send `/goal` and the objective in the composer. See [Set a goal with /goal](/coding-sessions/#goal-command).

If a startup step fails, the card shows **Session failed to start**, the step, and the reason. See [Session failed to start](/troubleshooting/#session-failed-to-start).

### Drafts [#drafts]

A draft keeps your message and your choices until you send it. It stays after a reload, on the device where you wrote it.

When the desktop app or a browser connects to a host on another computer, a reload removes the draft. The phone keeps its drafts on the phone.

OpenDucktor removes a draft 7 days after your last change. A draft that you did not change closes when you leave it.

You can keep more than one draft open. To remove a draft, select <Action>Discard</Action> in its header. If you changed the draft, confirm with <Action>Discard draft</Action>.

### Name work with a model [#naming-model]

When the workspace has a [Naming model](/settings-reference/#repository-agents-naming-model), the model names the work:

- The title of a new session comes from its first message. Until the model answers, the session shows the first words of the message. A title that you set yourself stays.
- A new worktree with an empty **Branch name** gets its branch name from the model, for example `perf/slow-notebook-search`. The startup step **Generate branch name and session title** shows it.
- A branch name that you type does not change.

If the model cannot name the branch:

- If the model fails, the branch is the [branch prefix](/settings-reference/#repository-configuration-branch-prefix) and the first words of the message, such as `odt/find-why-search-is-slow-in`. The startup step shows the error as a warning. The card shows **Session ready with a warning**.
- If the model does not answer in 15 seconds, the branch also comes from the message. No warning shows.

To change how the model names work, edit the [naming prompts](/agent-prompts/#naming).

## Use a custom role [#custom-roles]

A custom agent role, such as a code reviewer, gives a workspace session its own instructions.

<Steps>
<Step>Open **Settings**, then **Custom agent roles**, and select <Action>Add role</Action>.</Step>
<Step>Enter a **Name** and a **System prompt**, then select <Action>Save settings</Action>.</Step>
<Step>On the draft page of a new workspace session, choose the role in the role menu under the composer. It shows **No role** until you choose one.</Step>
</Steps>

Roles are available in every workspace.

## Create tasks from a request [#create-tasks]

Ask the agent to create tasks, for example:

<AgentMessage>{`
Let people export a notebook to Markdown and to PDF. Split this into tasks that each fit in one pull request. Search the board first, and do not create a task that exists.
`}</AgentMessage>

New tasks start in <Status of="open" />. Their first step depends on their [issue type](/tasks-and-workflows/#issue-types).

<Steps>
<Step>Each new task shows as a card in the session. Select <Action>Open</Action> on a card. The task details open.</Step>
<Step>Select the workflow action, for example <Action>Start Builder</Action>. Then select <Action>Run in background</Action>. The task session starts, and the workspace session stays open.</Step>
</Steps>

## Fork a workspace session [#fork]

<ProductDemo id="fork" />

A fork is a new workspace session with the conversation of the source session up to one reply. Use it to try another follow-up and keep the source session as it is.

<Action>Fork from this reply</Action> shows under the last reply of each completed turn. The fork keeps the harness, the model, the role, and the target branch of the source session.

| Work location | Where the fork works |
|---|---|
| **Same folder** | In the folder of the source session. The two sessions change the same files. |
| **New worktree** | In a new worktree, on a new branch from the last commit of the source folder. Uncommitted changes do not go to the new worktree. The source folder must have a commit. |

## Import a session from an external runtime [#import]

Continue in OpenDucktor a conversation that you started in OpenCode, Codex, Claude Code, or Antigravity.

<ProductDemo id="import-session" />

Select the arrow beside <Action>New task</Action>, then <Action>Import session from an external runtime</Action>. You can also run it from the [command palette](/command-palette/#actions).

The list shows only the main conversations that started in the repository folder or in one of its Git worktrees, and that no task or workspace session uses yet. For Codex, it also shows the sessions that you archived in Codex.

The import does not copy the conversation. OpenDucktor continues the same session, with the same session ID, in the same folder. It uses the title and the model of the session, and the default target branch of the repository. Antigravity lists no model for a session, so an imported Antigravity session keeps the model that it has in Antigravity.

The list stays current for 10 minutes. If an import fails with a message that ends with `Reload sessions.`, close the dialog and open it again.

## Archive a workspace session [#archive-a-session]

<Steps>
<Step>Select <Action>Archive</Action> in the session header.</Step>
<Step>For a session in a worktree, **Remove worktree and branch** is on. Archive then deletes the worktree and its branch. To keep them, turn it off. If another workspace session or an open task uses the worktree, OpenDucktor keeps it.</Step>
<Step>Select <Action>Archive session</Action>. The session moves to **Archived sessions**, and its agent and terminals stop.</Step>
</Steps>

To restore a workspace session, select the arrow beside <Action>New task</Action>, then <Action>Archived sessions</Action>, then <Action>Restore</Action> on the session.
