# Session Git comparison

## Choose a comparison branch

Use the Target branch editor in the Git panel to choose a local or remote-tracking branch. This changes comparison diffs, comparison counts, file-tree markers, and the Rebase destination. It does not change checkout, branch tracking, the repository default, or the upstream used by Pull and Push.

Task and workspace sessions use the same Git panel. The header has two rows. The first row shows the current branch, an arrow, the target branch, and the ahead and behind counts against the target. The branch names have no chip surface. The target name keeps its full width up to 45% of the row, and the current branch name shortens first. Each name keeps its full value in its title and its role in an accessible label. The second row shows the icon buttons Refresh, Rebase, Pull, and Push, and the Detect PR button at its right end. Each icon button keeps its tooltip and its count badge.

A click on the target chip opens searchable branch choices. In repository-root sessions, a click on the current-branch chip opens checkout choices. Worktree checkout rules stay the same. Help, loading, errors, and retry actions appear only in the target choices.

## Panel views

The panel has three tabs: Uncommitted changes, Branch changes, and History. A new Git context opens on Uncommitted changes. The tab row has content-width tabs and scrolls sideways in a narrow panel. Tab changes keep the commit draft, the file search, the open directories, and the open diffs of the same Git context. Every tab stays selectable. A click shows its tab at once, and a comparison that loads or fails does not change the selected tab. Branch changes shows the loading or failure state in its view and loads when its comparison is ready.

Uncommitted changes shows Unstaged and Staged groups, and a Conflicts group when Git has unresolved paths. Unstaged compares the index with the working files and includes ordinary untracked files. Staged compares `HEAD` with the index. A partly staged file shows in both groups. Each file and each text chunk can be staged, unstaged, or discarded. Local diffs show the raw Git hunks without text conversion or external diff drivers, so each shown chunk is the chunk that Git applies. A chunk action changes only the text of that chunk. If the chunk text or its lines changed after review, the action changes nothing and asks for Refresh. A submodule change has no chunk actions, and Discard refuses it, because Discard cannot change the commit that the submodule has checked out. Stage and Unstage change the whole submodule entry. A file-mode change moves only with a file action. Discard needs a confirmation. A pointer over a file row, or keyboard focus in it, shows the Discard, Stage or Unstage, and More actions buttons beside the line counts. A right-click on a file, or its More actions button, opens the file menu. View file in the menu opens the file preview, as the Files tab does. A deleted file has no View file item. Unstaged and Staged share the list height in two halves. Drag the handle between them, or focus it and use the Up and Down arrow keys, to change the split. A double-click on the handle restores the halves. A click anywhere on a group header opens or closes the group. A closed group keeps only its header, and the other group uses the space. The file count shows only while a search is active, as matches and total, for example `1/3`.

Stage, Unstage, and Discard run one at a time in a queue. A click during another change waits in the queue and does not fail. Stage and Unstage of a file or a group move the rows at once. Git returns the local changes after each write, and the panel shows them without another read. The next change uses the snapshots of that result. A failed change shows its error, reads the actual state again, and ends the changes that wait behind it. Chunk changes and Discard show their result when Git returns it. A Refresh or another read does not disable Stage, Unstage, or Discard. Chunk actions stay off while a change runs, because a change can move the chunks of a file. If the diff of a file changed after a chunk click, the chunk change stops and asks the user to review the chunk again.

The commit composer shows only in Uncommitted changes. It is one input group: the message field and an icon-only Commit button share one border and one height. Enter or the Commit button makes a commit from the staged content only. Cmd+Enter on macOS, or Ctrl+Enter on Windows and Linux, stages every change, then commits it. The field placeholder shows this shortcut. A disabled Commit button tells the reason in its tooltip. While a commit runs, the button shows a spinner, and a status message announces which commit runs. The draft stays in app memory for each Git context until Git confirms the commit.

History shows the commits of the current branch and the target that the other branch does not have. The shared base ends the graph. Older shared history stays out, and the graph marks edges that continue past the shared base. Later pages keep the branch tips of the first page. The list mounts only the rows that it shows, so a long History stays fast. A line above the list states the count when the branch is behind the target, and states a match when both branches point to the same commit. A header names the columns: Branch / Tag, Graph, Commit message, Author, Date, and SHA. A right-click on the header or its columns button opens the column choices. The commit message always shows, and Author and SHA start hidden. A title drags to a new place, and Alt with an arrow key moves the focused column. The choice stays on the device. The Branch / Tag column, left of the graph, shows every branch and tag of a commit. A local branch and its remote branches share one entry. The checked-out branch comes first, then the comparison target, then other branches, then tags. The first entry shows its name in the lane color, a line ties it to its node, and the other entries stack as small icons. A hover lists every entry with its full names. Each row is one line. Each branch tip starts a new lane right of the lanes above it, so the current branch never continues the column of commits that the target merged. A first parent stays in its lane and does not move into a branch on its right, so the target line keeps its lane down to the shared base. A node with the author photo marks a commit, and a small dot marks a merge. GitHub no-reply emails use the GitHub avatar. Other emails use Gravatar, which gets only the SHA-256 of the email. An author without a photo shows initials. A line keeps its color when new commits move the lanes. The current branch and the target main line use the first color of their side, and a merged branch takes its color from its commit ID. Branch commits use cool lane colors. Missing target commits use warm lane colors and a faded photo. A band in the lane color runs from the node to the commit text, and lines turn into other lanes with round corners. The row shows the subject, the body as one muted line, and a short age such as `3h`. A click on a row opens the commit details: author, relative and exact date, full message, branches and tags, branch side, and commit ID with a copy button. A scroll of the list closes the details. The graph uses at most 40% of the row width. A wider graph scrolls sideways, and all rows move together. A new commit of the same branch keeps the shown graph while its graph loads. Then the rows of older commits slide to their new place, and new commits fade in. Another branch, target, or directory starts without rows.

## Workspace choice lifetime

A workspace comparison choice stays in app memory across session changes, workspace changes, page exits, branch changes, and tools-panel closure. It resets on app reload or a confirmed successful archive of that session. A failed archive retains the choice. Selecting Tracked upstream in a repository-root session removes its branch override.

Task target choices continue to use the saved task record. Sessions for the same task share its saved target.

## Comparison failures

The panel keeps the selected target visible when its comparison fails. Target diffs, counts, markers, and Rebase stay unavailable until the selected comparison succeeds. Use Refresh to fetch the selected remote and retry, or choose an available branch. A branch-list error has a separate Retry branches control.

Uncommitted reads and change snapshots use `HEAD` and the index. File browsing, staging, Commit, and conflict recovery remain available when their own prerequisites hold. Pull and Push use actual branch tracking, even when the comparison branch differs.

A new task worktree can have upstream settings before its remote branch exists. A missing remote-tracking ref produces the untracked status, which permits the existing Push action to create the remote branch. Push shows the count of commits that no remote has, because its first push sends them. Comparison with another available branch remains usable. Other Git read errors remain visible.

If a task has no saved target and repository settings fail to load, the panel shows the settings error. Refresh retries that read. A saved task target remains usable when settings cannot load.

## Refresh

Every refresh reads the branch first and follows a branch that its own read finds. Focus and visibility refreshes fetch the selected target's remote when its five-minute fetch limit permits. Manual Refresh always attempts the fetch. Soft refresh reads local Git data without fetching. Concurrent refreshes for the same repository, directory, target, and checkout share a pending fetch.

Manual Refresh shows its pending state before any Git work starts. More clicks join the pending refresh. A Refresh that starts before the checkout is known belongs to the first checkout that the panel shows. Each session, target choice, and checkout keeps its own Refresh: a return shows its running Refresh, and a click joins it. A checkout from another place shows the new branch without the old Refresh state or failure. A branch that Refresh itself finds takes that Refresh. A new target choice starts its own Refresh, and a failure of the previous choice does not show for it. Loaded default settings keep the default choice, so that Refresh continues. The local changes read starts with the fetch, so a slow fetch does not delay it. Local changes also hold the upstream counts, so a manual Refresh reads them again after the fetch, and that read gives the result. Without a fetch, a failure of the first read stays, and the refresh reports it after the other steps end. If Refresh finds a new branch or loads missing settings, it continues with the new comparison, and it stays pending until that work ends. Its result includes a failure of that work. If another session or target opens before that work starts, the work ends without a read, because that view has its own refresh. Branch changes and History read again after the fetch ends. The file views read again after the Git steps, also when a Git step fails, because local files can change without the remote. They show their own state. A failed manual refresh keeps the last loaded changes and shows the failure until a later refresh succeeds. A failed read of local changes, Branch changes, or a shown History fails the manual refresh and the refresh after a Git action. A confirmed commit, change, push, pull, or rebase stays a success, and its message tells the user that the panel could not update. A background refresh leaves each read failure to the view that shows it. After a failed target check or fetch, the Git reads run one time and no read repeats.

A focus, soft, or action refresh reads both diff scopes and the shown History again. It ends when its view moves to another session or closes, also when the user returns. The returned view reads again by itself. A completed Git change keeps its original directory, and a late refresh error cannot appear in another session.

## Panel integration

The shared comparison control, check, refresh path, and read projection live in `packages/frontend/src/features/agent-studio-git`:

- `reads/use-git-panel-reads.ts` observes local changes and Branch changes with TanStack Query.
- `refresh/git-refresh-coordinator.ts` is plain TypeScript. It runs the refresh steps in order and keeps the manual Refresh state of each context.
- `refresh/use-git-refresh.ts` gives each render's view to the coordinator and starts the focus refresh.
- `session-comparison-view.ts` builds the panel data from the reads and the checked comparison.

Scope adapters own task persistence and workspace app memory. Keep Git action ownership mounted across tab and panel closure so a pending command retains its original directory, target, and operation lock. The dynamic-tabs task `openduckto-k0u1t` owns tab names and layout changes.

Each read uses the query keys of its directory, checkout, and comparison. A refresh step uses the keys of the render that made it, so a late result cannot enter another view. A context change cancels the unfinished reads of the old context. A closed panel keeps its reads, so a late result still validates restored comments.
