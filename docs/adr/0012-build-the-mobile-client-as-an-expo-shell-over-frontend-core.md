# Build the mobile client as an Expo shell over frontend core

## Context

Users want to follow and steer agent work on their hosts from a phone or tablet. A host already serves remote clients through the [remote host protocol](../remote-host-protocol.md), and `packages/frontend-core` already holds the client behavior that every client shares ([ADR 0011](0011-own-shared-client-behavior-in-a-platform-independent-package.md)).

A native client must keep the same session projection, history merge, recovery barrier, task stream acknowledgements, and drafts as desktop. It must also meet transport rules that a JavaScript socket factory alone does not prove: redirect rejection, normal certificate validation, cancellation, and binary terminal frames. React Native does not reload its runtime when the user changes the host, so each host connection must keep its own state in one JavaScript runtime.

## Decision

Build the mobile client in `apps/mobile` as an Expo SDK 58 app with a native UI. It is a remote client of one saved host at a time.

- The app composes the same frontend-core owners as desktop: runtimes, host runtime status, tasks, workspace activity, the agent orchestrator, session read state, and drafts. Behavior that mobile needs and that lived only in `packages/frontend` moves to frontend-core. Mobile adds only platform adapters, its local workspace selection, and native presentation.
- One `ClientConnection` exists for the active saved host. Selecting another host unmounts the connection tree, disposes the connection, and creates a new one. Host work continues.
- HTTP requests and event streams use an in-repo Expo module, `openducktor-network` (URLSession on iOS, OkHttp on Android). It never follows redirects, uses only platform trust evaluation, has no cookie store, cache, or credentials, streams the body with backpressure, and classifies failures from structured native data. The adapter maps a TLS failure to a permanent failure and a local network denial to a reason that names the permission.
- Terminals use the React Native WebSocket. iOS fails an upgrade without `Sec-WebSocket-Accept`. On Android, the network module sets the WebSocket client builder to refuse redirects.
- Drafts of each saved host stay on the device in a separate MMKV instance, with the same size limits and expiry as desktop local drafts. Removing a saved host deletes its instance. Desktop and web clients keep remote drafts in connection memory, as before.
- Terminals, math, and Mermaid diagrams render in isolated WebView pages that Bun builds from `apps/mobile` sources. The pages load no remote resource, block navigation, and exchange messages that both sides check with Zod. All other content renders natively.
- The mobile UI uses the desktop brand on a native shell: the native stack, JavaScript tabs with an app tab bar, and native sheets hold slate surfaces, outlined cards, the desktop status colors, Space Grotesk, IBM Plex Mono, and Lucide icons. A script generates the colors from `packages/frontend/src/styles.css`, and a test fails when they differ.
- The app creates no notification runtime and adds no notification library in the first version.

## Options we rejected

- Use `expo/fetch` for remote HTTP. It reports native failures only as localized text, so the app cannot tell a certificate failure from a network failure.
- Use Expo DOM components for terminals and rich blocks. They allow file access from file URLs and set no content security policy.
- Copy the client behavior into the mobile app. Session projection, recovery, and workflow rules would drift between clients.
- Keep remote drafts in connection memory on mobile. A mobile app is suspended and closed often, so drafts would be lost.
- Use only the iOS and Material 3 idioms, with system colors, the system font, and platform symbols. The app would lose the colors that make a task or a session readable at a glance.
- Share theme tokens through a new package. Desktop lane and badge colors are Tailwind palette classes, so a package would not give one source.
- Build with EAS Build. The release workflow uses GitHub Actions with Xcode and Gradle and needs no Expo account.

## Consequences

A change to shared client behavior lands in frontend-core and reaches desktop, browser, and mobile together.

The native network module is new native code that the repository owns. Its behavior must match the browser transport in `packages/frontend/src/lib/remote/transport.ts`.

`ios/` and `android/` are generated by `expo prebuild` and are not committed. Native settings live in the app config and the config plugins in `apps/mobile/plugins`.

React updates follow the React version of the Expo SDK, because the monorepo resolves one React copy.
